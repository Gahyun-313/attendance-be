# 🔧 Troubleshooting

## 🚨 동시 체크인에서 500 오류가 발생한 문제

### 문제

같은 학생이 동일 세션에 20개의 체크인 요청을 동시에 보내자 다음 결과가 발생했습니다.

- 정상 처리 1건
- 중복 체크인 409 응답 12건
- 서버 오류 500 응답 7건(35%)

애플리케이션에서 중복을 먼저 조회하고 DB Unique 제약도 사용했지만, 여러 요청이 모두 레코드가 없다고 읽은 뒤 동시에 INSERT를 시도했습니다. 일부 Unique 제약 예외가 공통 500 응답으로 노출됐습니다.

### 첫 번째 시도: 임계 구역에 분산 락 적용

사용자+세션 단위 Redisson 락으로 조회와 저장 구간을 감쌌습니다.

결과는 성공 1건, 409 13건, 500 6건(30%)이었습니다. 오류가 남아 있어 락만으로 해결되지 않았습니다.

### 두 번째 시도: 트랜잭션 종료 후 락 해제

메서드 내부에서 락을 해제하면 Spring 프록시가 실제 커밋하기 전에 다음 요청이 진입할 수 있었습니다. `TransactionSynchronizationManager`를 이용해 실제 트랜잭션 종료 이후로 해제를 미뤘습니다.

그러나 500 오류가 45%로 오히려 증가했습니다.

### 세 번째 시도: Redisson Watchdog 사용

고정 lease time이 부하 중 먼저 만료된다는 가설을 세우고 Watchdog 방식으로 변경했습니다. 결과는 이전과 동일해 이 가설이 원인이 아님을 확인했습니다.

### 실제 원인

서버 스택트레이스에서 계속 중복 INSERT가 발생하는 것을 확인했습니다. MySQL 기본 `REPEATABLE_READ`에서는 트랜잭션의 첫 SELECT 시점에 스냅샷이 고정됩니다.

체크인 로직은 분산 락을 획득하기 전에 NFC 태그를 조회합니다. 따라서 동시 요청들은 락을 기다리기 전에 각자의 스냅샷을 이미 고정했고, 락을 순서대로 획득해도 앞 요청이 커밋한 기록을 보지 못했습니다.

### 해결

- 사용자+세션 단위 Redisson 분산 락 유지
- 트랜잭션 완료 후 락 해제
- `checkIn()`의 격리 수준을 `READ_COMMITTED`로 변경
- 가변적인 락 점유 시간을 고려해 Watchdog 유지

최종 측정 결과는 성공 1건, 409 19건, 500 0건이었습니다.

### 배운 점

- 분산 락은 실행 순서를 제어하지만 트랜잭션이 바라보는 스냅샷까지 바꾸지는 않습니다.
- 이론적 추측보다 동일한 부하 테스트를 반복해 가설을 검증하는 것이 중요했습니다.
- 공통 오류 메시지만 보지 않고 실제 DB 예외 스택트레이스를 확인해야 원인을 좁힐 수 있었습니다.

## 🧪 Redisson 테스트 의존성 문제

Redisson은 Lettuce와 달리 Bean 생성 시 Redis 연결을 시도해 Redis가 없는 환경에서 `@SpringBootTest` 컨텍스트가 실패했습니다. 테스트 전용 `RedissonClient`를 `@Primary` Mock으로 제공해 외부 Redis와 통합 테스트를 분리했습니다.

이때 Redisson용 Connection Factory Mock이 `StringRedisTemplate`까지 오염시키지 않도록 두 의존성의 구성을 분리했습니다.

## ☁️ Docker·AWS 배포 중 발생한 문제

- Gradle Wrapper 실행 권한 누락: Dockerfile 빌드 단계에서 실행 권한 부여
- 운영 설정 파일의 잘못된 ignore: 안전한 환경변수 참조 파일은 추적하도록 규칙 수정
- HS256 Secret 길이 부족: 최소 256bit를 만족하는 랜덤 값으로 교체
- 소형 EC2 메모리 부족: 빌드와 실행 시 리소스 사용을 확인하고 인스턴스 재기동 후 복구

민감한 실제 IP, DB Endpoint, Secret은 공개 문서에 기록하지 않고 환경변수로 관리합니다.
