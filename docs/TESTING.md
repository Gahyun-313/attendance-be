# 🧪 Testing

## 🎯 테스트 전략

| Layer | Tools | 검증 대상 |
| --- | --- | --- |
| Unit | JUnit, Mockito | Service 규칙과 예외 처리 |
| Repository | `@DataJpaTest`, H2 | JPA 쿼리와 데이터 제약 |
| Integration | `@SpringBootTest`, MockMvc | 인증부터 DB까지 API 흐름 |
| Realtime | STOMP 테스트 페이지 | 연결·구독·출석 이벤트 수신 |
| Load | k6 | 응답 시간과 동시 체크인 |

사용자, 출석, 세션 Repository와 인증·사용자·출석 통합 흐름을 테스트했습니다. 조직 도입 후에는 다른 조직의 목록 미노출과 ID 직접 접근 차단도 통합 테스트에 추가했습니다.

## 🔒 동시 체크인 측정

같은 학생 토큰으로 동일 세션에 20개의 체크인 요청을 동시에 보냈습니다.

| Result | Before | After |
| --- | ---: | ---: |
| 정상 처리 | 1 | 1 |
| 409 Conflict | 12 | 19 |
| 500 Error | 7 (35%) | 0 (0%) |

DB Unique 제약만 사용했을 때 동시 INSERT 경합이 500으로 노출됐습니다. Redisson 분산 락과 트랜잭션 경계를 조정한 뒤 최초 1건만 처리되고 나머지는 의도한 409로 반환되는 것을 확인했습니다. 10만 건의 출석 데이터에서도 같은 결과를 재검증했습니다.

## ⚡ 조회 성능 측정

| Scenario | Result |
| --- | --- |
| 기존 데이터 통계 조회 | 평균 9.27ms / p95 16.04ms / 실패율 0% |
| 10만 건 + Redis 캐시 | 평균 8.63ms / p95 14.28ms / 실패율 0% |
| 출석 기록 정렬 쿼리 | 복합 인덱스 적용 후 `using_filesort` 제거 |

두 통계 측정은 데이터 규모가 다르므로 단순한 동일 조건 속도 비교가 아닙니다. 데이터가 크게 증가한 환경에서도 캐시를 적용해 응답 수준을 유지했다는 근거로 사용합니다.

## 🧱 테스트 환경 분리

Redisson은 애플리케이션 시작 시 Redis 연결을 시도하므로 통합 테스트에서는 `RedissonClient` 테스트 설정을 별도로 구성했습니다. DB 흐름을 검증하는 테스트는 캐시를 비활성화해 로컬 Redis 실행 여부에 영향을 받지 않게 했습니다.
